배포 후 발견된 두 가지 데이터 동기화 버그를 진단하고 해결했다. ① 백엔드는 기존 경기 재저장(PUT) 시 unique 제약 위반으로 500을 던지던 문제, ② iOS는 앱을 켤 때마다 라벨링한 경기가 "라벨링 큐"에 중복으로 다시 뜨던 문제다. 두 버그 모두 실제 서버 로그와 단말 SQLite store를 직접 열어 원인을 확정한 뒤 수정하고 재현 테스트로 검증했다.

A 백엔드 — "지표 재계산"이 저장되지 않는다

한 쿼터의 운동 데이터가 0으로 저장된 경기를 재계산하면 화면엔 반영되는데, 다시 들어가면 0으로 되돌아갔다.
증상Bug

iOS에서 "지표 재계산"을 누르면 화면(메모리)엔 값이 반영되지만, 경기 화면을 나갔다 다시 들어오면 다시 0으로 보였다. 즉 로컬 계산 결과가 서버에 반영되지 않고, 화면 재진입 시 서버의 옛 값(0)이 로컬을 덮어쓰고 있었다.

진단 — EC2 서버 로그

iOS 콘솔에는 unauthorized(401)만 보여 처음엔 토큰 문제로 의심했으나, 토큰은 곁가지였다. AWS EC2의 백엔드 컨테이너 로그(docker logs kicklog-backend)를 직접 확인하니 진짜 원인이 드러났다:

ERROR ... DataIntegrityViolationException: duplicate key value violates
  unique constraint "quarter_workouts_match_id_quarter_number_key"
  Detail: Key (match_id, quarter_number)=(8, 2) already exists.
    at MatchService.saveMatch(MatchService.kt:32)
    at MatchController.upsert(MatchController.kt:35)

재계산 PUT이 서버에서 500 (unique 제약 위반)으로 실패하고 있었다. 그래서 서버엔 0이 그대로 남고, 재진입 시 그 0이 로컬을 덮어쓴 것이다.

근본 원인 — JPA IDENTITY + clear() 재삽입의 함정

Match.replaceWith()는 경기를 갱신할 때 쿼터를 이렇게 처리했다:

quarterWorkouts.clear()                       // 기존 쿼터 DELETE "예약"
command.quarters.forEach { quarterWorkouts.add(QuarterWorkout(...)) }  // 새 쿼터 INSERT "예약"

QuarterWorkout.id는 @GeneratedValue(strategy = IDENTITY)다. IDENTITY 전략은 INSERT를 실행해야 PK를 얻으므로, Hibernate가 새 INSERT를 즉시 발행한다. 반면 clear()로 인한 orphan DELETE는 트랜잭션 flush 마지막에 실행된다. 그 결과:

  • DB에 이미 (match_id=8, quarter_number=2) 가 존재
  • 재계산 PUT → 새 (8, 2) INSERT가 기존 행 DELETE보다 먼저 실행
  • → unique 제약 위반 → 500 → 저장 실패

즉 최초 저장(INSERT)만 성공하고, 이미 존재하는 경기를 수정하는 모든 PUT이 항상 실패하는 구조였다. (재계산·재라벨링 모두 해당)

왜 테스트가 못 잡았나

교훈

기존 통합 테스트는 H2 인메모리 DB(ddl-auto: create-drop, flyway.enabled: false)로 돌았다. unique 제약은 Flyway 마이그레이션 SQL에만 있고 엔티티에는 없어서, 테스트 스키마에는 제약이 생성되지 않았다. 그래서 이 버그가 테스트를 통과해 버렸다.

해결Fixed

쿼터를 갈아엎지 않고 quarter_number 기준 in-place 동기화로 변경했다:

val incoming = command.quarters.associateBy { it.quarterNumber }
quarterWorkouts.removeIf { it.quarterNumber !in incoming.keys }   // 빠진 것만 DELETE
command.quarters.forEach { cmd ->
    existing[cmd.quarterNumber]?.updateFrom(cmd)                  // 기존은 UPDATE
        ?: quarterWorkouts.add(QuarterWorkout.from(this, cmd))    // 새 것만 INSERT
}

같은 (match_id, quarter_number) 행을 갱신(UPDATE)하므로 INSERT-before-DELETE 충돌이 원천 제거된다. 추가로 엔티티에 unique 제약을 명시(@Table(uniqueConstraints=…))해 운영 스키마와 정합을 맞추고, 회귀 테스트가 H2에서도 이 버그를 잡도록 했다.

B iOS — 앱을 켤 때마다 라벨링한 경기가 큐에 다시 뜬다

앱을 강제 종료 후 재실행(또는 재부팅)하면, 이미 라벨링을 끝낸 경기들이 "라벨링 대기 큐"에 중복으로 다시 나타났다.
배경 — 기기 재설치로 로컬이 비워진 뒤Bug

앱스토어 배포 후 앱을 삭제→재설치하면 로컬 SwiftData store와 HealthKit anchor(어디까지 가져왔는지 기록)가 함께 사라진다. 이후 앱이 두 경로로 데이터를 복구한다:

  • 백엔드 복구 — 서버에 백업된 라벨링 경기를 내려받음 → "최근 경기"
  • HealthKit 재import — anchor가 없어 가입일 이후 워크아웃을 처음부터 다시 가져옴 → "라벨링 큐"

이 둘이 같은 워크아웃을 가리키는데도 서로를 알아보지 못해, 한 경기가 "최근 경기(라벨)"와 "라벨링 큐(미라벨)"에 동시에 나타났다.

진단 여정 — 가설을 단말 데이터로 검증

로그만으로는 한계가 있어, idevicesyslog / devicectl로 단말의 실제 SwiftData store 파일을 PC로 복사한 뒤 sqlite3로 직접 열어 가설을 하나씩 검증했다.

1
가설: store가 매번 비워진다(영속화 실패)? → store 파일 확인 결과 default.store 148KB + WAL 2.1MB로 데이터는 정상 영속화되고 있었다. 가설 기각.
2
그렇다면 store 안에 중복이 실재한다. ZMATCH 테이블을 보니 4경기가 각각 "라벨 + 미라벨" 쌍으로 존재(같은 playedAt).
3
결정적 단서: 라벨 경기와 미라벨 경기의 쿼터를 비교하니 —
matchPK  lbl     quarters
4        라벨    0      ← 라벨 경기에 쿼터가 하나도 없음!
8        미라벨  3      ← 쿼터(진짜 HealthKit UUID)는 미라벨 쪽에만

근본 원인 — 복구가 "목록"만 가져와 쿼터가 비었다

앱 시작 시 백엔드 복구는 목록 API(summary)를 호출했는데, 목록 응답에는 쿼터가 들어있지 않다(쿼터는 상세 API에만 있음). 그래서 라벨 경기가 쿼터 없이 복구됐고, 이로 인해:

  • import 중복 제거(sourceWorkoutUUID/시각 매칭): 라벨 경기에 비교할 쿼터가 없음 → 매칭 실패 → 미라벨 생성
  • cleanup(라벨 쿼터 시각 집합): 집합이 비어 guard !isEmpty에서 즉시 종료 → 중복 못 치움

즉 "복구 → import 순서"와 "중복 제거 로직"을 갖춰도, 비교 기준이 될 쿼터 자체가 없어서 모두 무력했다.

해결 — 3겹 방어Fixed

① 순서 보장 + ② 상세 복구 — 앱 시작 시 HealthKit import보다 먼저 백엔드를 복구하되, 목록뿐 아니라 각 경기의 상세(쿼터 포함)까지 내려받는다:

// 목록으로 serverId 수집 후, 각 경기 상세까지 복구
for serverId in serverIds { _ = try? await fetchMatch(serverId: serverId, into: context) }

이제 라벨 경기에 쿼터(healthKitWorkoutId = 진짜 HealthKit UUID)가 채워져, import가 "이 워크아웃은 이미 라벨 경기에 있다"고 UUID로 정확히 인식해 미라벨을 아예 안 만든다.

③ 빈 껍데기 정리 — SwiftData에서 sourceWorkoutUUID는 unique라, 상세 복구로 같은 UUID 쿼터를 만들면 기존 미라벨의 쿼터가 라벨 경기로 흡수된다. 그 결과 미라벨이 "쿼터 0개인 빈 껍데기"로 남는데, 기존 cleanup은 이를 못 치웠다. 그래서 cleanup이 빈 미라벨도 삭제하도록 보강:

let isEmpty = match.quarters.isEmpty          // 쿼터가 흡수돼 빈 껍데기
let isDuplicate = match.quarters.contains { 시각이 라벨과 겹침 }
if isEmpty || isDuplicate { modelContext.delete(match) }

순서 보장(①)으로 정확도를 높이고, 상세 복구(②)로 dedup이 UUID로 작동해 새 중복을 원천 차단하며, 빈 껍데기 정리(③)로 기존에 쌓인 중복을 청소한다.

검증 — 단말 store + cold-start 재현

검증 완료
시점라벨 경기미라벨(중복)
수정 전4 (쿼터 0)4 (쿼터 3·3·3·…)
수정 빌드 첫 실행4 (쿼터 9) ✅0 ✅ 콘솔: "중복된 미라벨 매치 4건 정리"
앱 강제 종료 후 재실행(cold start)4 (쿼터 9)0 — 재발 없음 ✅

수정 전에는 cold start마다 미라벨 4개가 생겼지만, 수정 후에는 재실행해도 0개를 유지했다. 단말 store를 직접 복사해 SQLite로 확인한 객관적 결과다.

C 교훈

  • 로그가 가리키는 곳을 끝까지 따라간다. iOS의 401은 곁가지였고, 진짜 원인은 서버의 500(unique 위반)이었다. 클라이언트 증상만 보면 엉뚱한 곳을 고친다.
  • ORM의 실행 순서를 이해한다. JPA IDENTITY + 컬렉션 clear() 재삽입은 "INSERT가 DELETE보다 먼저" 실행되는 고전적 함정이다. "전부 지우고 다시 넣기"보다 in-place 갱신이 안전하다.
  • 제약은 엔티티에도 명시한다. 제약이 마이그레이션 SQL에만 있으면, 인메모리 테스트 DB가 제약을 안 만들어 회귀를 놓친다.
  • 증상이 막히면 데이터를 직접 열어본다. "store가 비워진다"는 그럴듯한 가설을 단말 SQLite를 직접 복사·조회해 기각했고, 진짜 원인(쿼터 0개)을 한 줄의 쿼리로 확정했다.
  • 동기화는 "양쪽이 서로를 알아보는 키"가 핵심이다. 라벨/미라벨이 같은 워크아웃임을 식별할 키(healthKitWorkoutId)가 한쪽에 없으면, 아무리 정교한 dedup도 작동하지 않는다.
