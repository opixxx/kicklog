결론: 전반적으로 컨벤션 준수가 잘 된 성숙한 코드베이스. 가장 가치 있는 리팩토링은 DB 성능 3건 (N+1 · 중복 인덱스 · HikariCP 풀) — ADR-0011 부하테스트 2차 측정의 전제 조건이며, 수정 전후를 수치로 입증할 수 있어 포트폴리오 가치가 가장 높다.

P1DB 최적화 — 실질 성능 이슈 (검증 완료)

셋 다 ADR-0011 부하테스트 측정 결과와 직접 연결된다. 2차 측정 전에 수행 권장.
HighMatch.quarters N+1 쿼리

Match.quarters 가 LAZY 인데 목록 쿼리 3개 모두 fetch join / @EntityGraph 가 없다. MatchService.initialize() 의 match.quarters.size 부작용과 SeasonStatService 의 .onEach { it.quarters.size } 가 경기 1건당 1쿼리를 유발한다. 유저당 300경기면 시즌 집계 한 번에 300+ 추가 쿼리 — 부하테스트의 seasons p95 2.65s 와 정합하는 1순위 의심점.

📄 MatchRepository.kt:15-61 · MatchService.kt:120-123 · SeasonStatService.kt:70 · Match.kt (quarters LAZY)
목록 쿼리에 JOIN FETCH 또는 @EntityGraph(attributePaths = ["quarters"]) 적용 후 initialize()/.onEach 제거. 페이지네이션 쿼리는 컬렉션 fetch join 시 Hibernate 메모리 페이징 경고 → id 페이징 → WHERE m.id IN fetch join 2단계 권장.
HighHikariCP 풀 미설정 (측정된 1차 병목)

application.yml 에 hikari 설정이 없어 기본값 maximum-pool-size = 10. ADR-0011 에서 "DatabaseConnections 가 테스트 내내 정확히 10.0 에 붙어 있었다"로 직접 측정된 병목이다.

📄 application.yml (hikari 블록 부재) · docs/adr/0011
spring.datasource.hikari.maximum-pool-size: ${DB_POOL_SIZE:10} 환경변수화. RDS 인스턴스 커넥션 한도와 함께 결정하고, 부하테스트 프로파일에서 30 으로.
Medium중복 인덱스 — V7 이 V5 의 접두사

V7 의 idx_matches_user_played_at(user_id, played_at) 은 V5 의 idx_matches_user_played_at_id(user_id, played_at DESC, id DESC) 접두사라 순수 쓰기 비용 + 인덱스 블로트.

📄 V7__match_metrics.sql:16-17 · V5__matches.sql:17
V15__drop_redundant_match_index.sql → DROP INDEX IF EXISTS idx_matches_user_played_at;
선택hibernate batch / fetch size 명시

hibernate.jdbc.batch_size: 50, default_batch_fetch_size: 100 — N+1 의 안전망. fetch join 적용 시 우선순위 낮음.
