# ADR-0017: 외부 의존 지연 하의 동시성 처리 모델 — 가상 스레드는 "스레드가 천장일 때"만 유효하다

- **Status**: Accepted (측정·판정) / **운영 적용은 조건부 보류** — ADR-0010 D2 와 같은 기준
- **Date**: 2026-10-30
- **선행 ADR**: ADR-0010 (keepalive lifecycle — 공유 자원 큐잉), ADR-0011 (HikariCP 풀=10 이 DB 동시성 하드캡), ADR-0014 (시즌 통계 DB 집계 전환), ADR-0016 (단일 박스 통합)
- **하네스**: `tools/loadtest/` (mock upstream · backend-ctl · run-measurement · watch · grafana-shot), `infra/terraform-loadtest/k6/` (w-ext · w-ext-ramp · w-dbpool · w-db · w-mix), `infra/loadtest-observability/` (Prometheus + Grafana + image renderer)
- **측정 산출물(로컬·gitignore)**: `docs/research/scenario1/` — 측정 기록 README, 원본 CSV, Grafana PNG

## Context

운영 백엔드는 **동기 블로킹**(`spring-boot-starter-webmvc`) + Tomcat 스레드 200 + HikariCP 10 구성이다.
인증 경로(`AppleIdentityVerifier`, `KakaoOAuthClient`)가 외부 HTTP 를 호출하는데, 이 호출이 느려지면
어떤 일이 벌어지는지, 그리고 어떤 기술이 그 문제를 해결하는지를 **측정으로** 가린다.

**가설**

- **H1**: 외부 의존 지연이 길어지면 동시 처리 가능 요청 수가 Tomcat 스레드 상한에 묶여
  처리량이 평탄화한다. 천장 = `threads.max ÷ 응답시간`.
- **H2**: 가상 스레드는 **스레드가 천장일 때만** 유효하다. DB 커넥션 풀이 천장인 워크로드에서는
  효과가 없다.

H2 가 핵심이다. H1 만 확인하면 "가상 스레드를 켜라"로 끝나지만, H2 가 **적용 범위를 가른다.**
반증 장치 없이 얻은 개선 수치는 과적용으로 이어진다.

**결과 요약**: H1·H2 **모두 확인**. 외부 HTTP 바운드에서 가상 스레드는 **7.4배 이상**,
DB 풀 바운드에서는 **0.8%(측정 오차 내)**. 따라서 KickLog 에서 유효한 적용 범위는 **인증 경로뿐**이다.

## 측정 셋업

| 구성 | 값 |
|---|---|
| 백엔드 | 같은 jar(`kicklog-0.0.1-SNAPSHOT.jar`), JDK **21.0.4**(temurin) 런타임, `-Xmx2g`, `SPRING_PROFILES_ACTIVE=loadtest` |
| 호스트 | Apple Silicon 8 vCPU / 16 GB — k6 · 백엔드 · mock upstream · Postgres 동거 |
| mock 외부 의존 | `tools/loadtest/mock-upstream.mjs` (Node, 지연 주입, 별도 프로세스) |
| 부하 | k6 v1.7.1 `constant-arrival-rate` (이산) + `ramping-arrival-rate` (관찰용) |
| 관측 | Prometheus 2s 스크레이프 + Grafana, **actuator 는 전용 관리 포트 8081** |

**전 구성이 같은 바이너리이고 환경변수만 다르다.** 바이너리가 다르면 처리량 차이를 설정에 귀속할 수 없다.

### 워크로드를 셋으로 분리한 이유

구속 자원을 귀속하려면 자원을 섞으면 안 된다.

| 워크로드 | 성격 | 구속 자원 가설 |
|---|---|---|
| **W-EXT** | 외부 HTTP 1회, **DB 미접촉** | Tomcat 스레드 |
| **W-DB-POOL** | DB 커넥션 점유, **외부 미접촉** | HikariCP 커넥션 |
| W-MIX | 혼합 | 먼저 포화하는 쪽 (본 ADR 미측정) |

### 측정 유효성의 전제 (수용 조건)

| 조건 | 왜 필요한가 | 결과 |
|---|---|---|
| mock 이 목표 주입의 3배를 소화 | mock 이 먼저 포화하면 백엔드 천장을 볼 수 없다 | ✅ **8,878 rps** @ p95 206ms (이상치 200ms 대비 +6ms) |
| `dropped_iterations` 분리 기록 | open model 이라 미기록 시 처리량이 과대계상된다 | ✅ 전 회차 |
| 포화 시점 CPU 동시 수집 | 천장을 하드웨어/설정에 귀속하려면 필수 | ✅ `process.cpu.usage` · `system.cpu.usage` |
| 설정이 실제로 적용됐는지 확인 | env 를 줬다고 적용됐다고 믿으면 안 된다 | ✅ `tomcat.threads.config.max` 교차확인 |

### 지연을 길게 잡은 이유

주입 지연을 **500ms** 로 늘려 천장을 `200 ÷ 0.5` = 400 rps 로 끌어내렸다.
지연 200ms 면 천장이 1,000 rps 인데, 같은 호스트에서 부하 생성기가 함께 도는 환경에서는
그 지점에서 호스트가 포화해 **"천장이 스레드인가 CPU인가"를 귀속할 수 없다.**

지연을 바꾸면 천장이 따라 움직인다는 사실 자체가 가설의 증거다. 단일 평탄화보다 강하다.

### B. W-DB-POOL — DB 커넥션 풀 바운드 (지연 50ms)

현실 쿼리로는 **이 환경에서 풀 구속 구간을 만들 수 없었다.** 시즌 집계가 p50 **3.3ms** 라
(ADR-0014 효과) 풀 10 의 천장이 `10 ÷ 0.0033` ≈ 3,000 rps 인데 호스트가 거기 못 미친다.
풀을 2 로 낮춰도 천장이 ~2,000 rps 로 여전히 구속되지 않았다.
그래서 W-EXT 에서 외부에 지연을 준 것과 **대칭으로** DB 에도 지연을 주입했다
(`/loadtest/db` → `SELECT 1 FROM pg_sleep(?)`). 측정 대상은 쿼리 내용이 아니라 **커넥션 점유 시간**이다.

## 기술 후보와 트레이드오프

비교 축은 **"규모가 커져도 유지되는가"** 다. 현 운영 환경(2GB 단일 박스)의 메모리 예산은
이 비교의 기각 근거로 쓰지 않는다 — 두 규모를 섞으면 논증이 깨진다.

| 후보 | 효과 | 비용 | 판정 |
|---|---|---|---|
| ① Tomcat 스레드 200 → 800 | 천장 3.98배 (측정) | 스레드당 스택 메모리, 컨텍스트 스위칭. **지연이 2배면 천장이 절반**으로 돌아온다 | **기각** (D2) |

## Decisions

### D1. 구속 자원은 워크로드가 정한다 — 천장 = `자원 수 ÷ 점유 시간`

| 워크로드 | 구속 자원 | 예측 | 실측 | 오차 |
|---|---|---:|---:|---:|
| W-EXT (스레드 200) | Tomcat 스레드 | 400 | 395 | 1.3% |
| W-EXT (스레드 800) | Tomcat 스레드 | 1,600 | 1,572 | 1.8% |
| W-DB-POOL (풀 10) | HikariCP 커넥션 | 200 | 193 | 3.5% |

세 지점에서 **계산값과 실측이 4% 안에서 일치**한다. ADR-0011 의 `10 conn × 28ms ≈ 350 ops/s`,
ADR-0010 의 `평형 TIME_WAIT = RPS × 60s` 와 같은 방식이다 — 모델이 현실을 설명한다.

### D2. 후보 ① 스레드 증설은 **기각** — 효과 상한을 재는 용도로만 썼다

스레드를 4배로 늘리면 천장도 3.98배가 된다. 구속 자원이 스레드임은 이걸로 확정됐다.
**그러나 구조는 그대로다.** 2,000 주입에서의 서명(평탄화 + drop 254/s + p95 2,440ms)이
기준선의 500 주입 서명과 동일하다. 천장을 옮겼을 뿐,
**"지연이 길어지면 스레드가 비례해 필요하다"는 관계는 남는다.**

외부 의존이 1초로 느려지면 800 스레드로도 800 rps 밖에 못 받는다 —
**우리 용량 산정이 통제 불가한 외부 SLA 에 묶인다.**
ADR-0010 이 `ip_local_port_range` 확장을 "천장 상향일 뿐 본질 해결 아님"으로 기각한 것과 같은 기준이다.

### D3. 천장은 **하드웨어가 아니다** — 판정 기준 G6 충족

기준선이 395 rps 에 막힌 그 순간 backend CPU 는 **3.1%** 다 (램프 측정에서도 최대 7.49%).
처리량이 꺾였는데 CPU·메모리·DB 가 모두 여유다. **서버를 키워도 이 숫자는 오르지 않는다.**

"스케일 업" 이 가장 흔한 반사 반응이고, 그게 통하지 않음을 수치로 가른 것이 본 측정의 핵심 가치다.

### D4. 후보 ② 가상 스레드 — **기술적 채택, 운영 적용은 보류**

**채택 근거**: 가상 스레드는 **지연과 스레드 수의 비례 관계 자체를 끊는다.**
2,935 rps 를 처리하면서 플랫폼 스레드는 **30개**(기준선 218, 후보① 818)이고,
p95 가 502ms — 주입 지연 그 자체다(큐 대기 ≈ 0).

**적용 범위는 외부 HTTP 를 타는 경로로 한정한다 (H2 의 결과).**

| KickLog 경로 | 성격 | 호출 조건 | 효과 |
|---|---|---|---|
| `GET /places/search` (Kakao Local) | 외부 HTTP 바운드 | **새 운동장 등록 시 검색 입력** | **7.43배 이상** |
| `POST /auth/*/signin` (JWKS fetch, 토큰 교환) | 외부 HTTP 바운드 | 최초 설치·90일 재로그인 | **7.43배 이상** |
| 경기 목록 · 시즌 통계 · 친구 목록 | DB 바운드 | 상시 | **없음** |
| `POST /auth/refresh` | **DB 바운드** | 액세스 토큰 만료마다 | **없음** |

*"가상 스레드를 켜서 7배"* 라고 쓰면 **과장**이다. 상시 트래픽(조회·토큰 갱신)은 전부 DB 바운드다.

**그런데 외부 바운드 두 경로 모두 노출이 작다.**

- `/places/search` 는 **새 운동장 등록 시에만** 호출된다. 저장된 운동장은 `GET /venues` 로
  DB 에서 읽고(`Venue` 가 name·좌표·주소를 자체 보관), 같은 장소 재등록도 멱등이다
  (`findByUserIdAndProviderAndProviderPlaceId`). iOS 는 450ms 디바운스 + 이전 요청 취소
  (`VenueSelectionScreen.swift`)라 등록 1건당 호출 1~3회다. 조기축구는 같은 구장에서 반복하므로
  사용자당 평생 운동장 2~5개 수준이다.
- `/auth/*/signin` 은 refresh 토큰 90일 주기라 사실상 최초 설치 시점에 몰린다.

따라서 **트래픽 양으로 이 천장에 도달하는 시나리오는 현 서비스 구조에서 만들어지지 않는다.**
천장에 닿으려면 `외부 호출 rps × 외부 지연 ≥ 200` 이어야 하는데, 두 경로 모두
운영 규모가 커져도 그 곱이 한 자릿수를 넘기 어렵다.

**채택 조건**

1. **런타임 JDK 21+**. `spring.threads.virtual.enabled` 는 런타임 체크이므로
   빌드 toolchain 은 17 그대로 둘 수 있다. 단 `backend/Dockerfile` 의 런타임 스테이지가
   Corretto **17** 이므로 배포하려면 이것을 21 로 올려야 한다.
2. **pinning 확인**. 이 측정에서는 pinning 이 없었다 — JEP 353/373 으로 `java.net.Socket` 이
   NIO(`NioSocketImpl`) 기반으로 재구현돼 블로킹 소켓 읽기가 캐리어를 붙잡는 대신 가상 스레드를
   park 하기 때문이다. `HttpURLConnection` 의 `synchronized` 는 keep-alive 캐시 같은 짧은
   장부 작업에만 걸려 IO 구간을 감싸지 않는다. **다른 라이브러리에서는 결과가 다를 수 있으므로
   도입 시 재확인한다** (JDK 24 의 JEP 491 전까지 `synchronized` 안의 블로킹은 pinning 한다).
3. **thread-local 의존 재점검**. MDC(`TraceIdFilter`) · Sentry 스코프가 thread-local 기반이다.
   요청당 가상 스레드는 새로 생기므로 전파가 끊기지 않는지 확인이 필요하다.

**보류 이유**: 현 운영 트래픽에서 이 천장에 닿지 않는다. ADR-0010 D2 와 같은 기준 —
*"측정으로 메커니즘은 확정했지만 현 규모에선 큰 이득이 아님을 인정. 과적용보다 함정을 알고 보류가 성숙한 선택."*

**해제 조건**: 아래 중 하나가 성립할 때 재검토한다. 트리거는 트래픽 양이 아니라
**점유 시간이 긴 외부 호출이 상시 경로에 생기는 것**이다.

1. **외부 호출을 타는 상시 기능이 추가될 때.** 예: 경기 저장마다 LLM 분석을 동기 호출하면
   점유 시간이 수 초~수십 초가 되고, 호출 빈도가 **경기 수에 비례**한다(운동장과 달리 캐시 불가).
   분석 10초 · 경기 저장 14 rps 면 동시 점유가 140 스레드로 천장의 70% 다.
   → 이 경우 먼저 **비동기화**를 검토한다. 요청 경로에서 기다리지 않으면 천장 문제 자체가 사라진다.
2. Kakao Local 응답 p95 가 **1초를 넘는 구간이 반복**될 때. 그 시점의 천장은 `200 ÷ 1s` = 200 rps.
3. 외부 호출 경로의 `tomcat.threads.busy` 가 상한의 50% 를 지속적으로 넘을 때.

### D5. 후보 ④ WebFlux 는 **측정 없이 기각**

효과는 ②와 비슷할 것으로 보이나 비용이 비대칭이다 — 전 계층 재작성, JPA 가 여전히 블로킹이라
`boundedElastic` 으로 밀어내야 하고(결국 스레드 풀로 회귀), 1인 유지보수에서 디버깅 난이도가 급증한다.
**같은 효과를 설정 한 줄로 얻을 수 있을 때 아키텍처 전환은 정당화되지 않는다.**

### D6. 커넥션 풀링 단독 도입은 **이득 없음** (통제군이 확정)

스레드를 그대로 두고 HTTP 클라이언트만 `JdkClientHttpRequestFactory`(풀 보유)로 바꾸면
천장이 **392.5** — 기준선 395 와 같다. 오히려 p95 가 나빠지고(574ms → 735ms)
플랫폼 스레드가 218 → 400 으로 늘어난다(`java.net.http.HttpClient` 의 자체 selector·executor).

**이 통제군이 측정의 핵심 장치다.** 없으면 후보 ②의 개선을 "가상 스레드 덕분"인지
"클라이언트를 바꿔서"인지 구분할 수 없다.

### D7. H2 확인 — 가상 스레드는 풀 바운드에서 **무효**

풀 10 에서 플랫폼 193 → 가상 192. 변화 **0.8%** 로 측정 오차 안이다.

가장 선명한 증거는 자원 상태 차이다. ①에서는 **두 자원이 모두 포화**한다
(커넥션을 기다리는 요청이 그동안 스레드를 쥐고 있기 때문). ②는 스레드 상한을 제거해
그 포화를 없앴는데 **처리량이 같다.** 즉 **스레드 포화는 결과였지 원인이 아니었다.**

③이 귀속을 확정한다 — ②와 ③의 차이는 풀 크기뿐이고(10 → 50) 여기서만 192 → 499 이상으로 오른다.

단, 가상 스레드가 전혀 무용하지는 않다: 주입 500 에서 p95 가 4,063ms → 3,169ms (**22% 감소**).
커넥션 대기 요청이 스레드 큐에서도 경합하던 것이 사라지기 때문이다.
**다만 처리량 천장을 올리지 못하므로 용량 문제의 해법은 아니다.**

### D8. ADR-0014 가 병목의 위치를 옮겼다

ADR-0011 당시 풀 10 에서 356 rps 천장이었다면 커넥션 점유 시간은 28ms 였다.
현재 시즌 집계는 p50 **3.3ms** — **약 10배 빨라졌고**, 그 결과 풀 10 의 천장이 약 3,000 rps 로
올라가 **커넥션 풀은 더 이상 구속 자원이 아니다.**
ADR-0011 D2("풀 10 이 DB 동시성 하드캡")는 **그 시점의 코드에 대한 판정**이며 현재는 해당하지 않는다.

### D9. 측정 방법론 — 관측 경로를 측정 대상과 분리한다

1차 측정에서 **가장 중요한 구간의 CPU 데이터가 통째로 비어 있었다.** Tomcat 스레드 200 개가
전부 부하 요청에 잡혀 있어 Prometheus 스크레이프도 같은 풀에서 대기하다 타임아웃했기 때문이다.
Grafana 의 `spanNulls` 가 그 공백을 직선으로 메워 **오독할 뻔했다.**

→ `management.server.port` 를 **8081 로 분리**(자체 커넥터·자체 스레드 풀) + `spanNulls: false`.
**관측 경로가 측정 대상과 자원을 공유하면 가장 중요한 순간에 관측이 실패한다.**

### D10. 무효 측정을 차단한다

k6 가 `setup()` 에서 죽으면 `http_reqs` 에 setup 요청만 남아 **그럴듯한 숫자**가 나온다
(실측: 처리량 216 rps · p95 3.6ms — 평탄화로 오독할 수 있는 가장 위험한 실패).
→ 러너가 `k6 종료코드 ≠ 0` 또는 `VU 반복 = 0` 이면 해당 회차를 `INVALID` 로 기록한다.

같은 이유로 `workload_duration` Trend 를 분리했다 — `setup` 의 토큰 요청 100건이
`http_req_duration` 에 섞여 p50 3.5ms / p95 394ms 로 분포가 두 덩어리로 갈렸다.

### D11. 본 측정에서 **지금 당장 적용할 것** — 인증 경로 타임아웃

가상 스레드는 보류지만, 외부 호출 경로를 전수 조사하는 과정에서 **운영에 실재하는 결함**이 나왔다.
이것은 동시성 모델과 무관하게 즉시 고친다.

| 항목 | 현재 | 위험 |
|---|---|---|
| `AppleIdentityVerifier` · `KakaoOAuthClient` | `RestClient.create()` — **타임아웃 미설정** | `HttpURLConnection` 기본값 0 = 무한 대기 |
| Apple JWKS | **매 로그인마다 fetch** (캐시 없음) | 외부 호출 빈도가 불필요하게 높음 |
| `server.shutdown: graceful` | 운영 미설정 (loadtest profile 에만 존재) | 배포마다 in-flight 요청 절단 |

**타임아웃 부재가 가장 위험하다.** 외부가 거부(connection refused)하는 게 아니라 **응답을 안 하고
물고 있으면** 그 스레드는 영구 점유된다. 초당 1건만 와도 200초면 Tomcat 스레드 200개가 전부 소진되고,
그 순간 로그인뿐 아니라 **경기 목록·시즌 통계까지 전부 멈춘다.** 트래픽 규모와 무관하다.

같은 리포의 `KakaoLocalRestClient` 는 공유 `restClientBuilder`(connect 2s / read 3s)를 써서 멀쩡하다 —
**인증 두 곳만 빠져 있다.** 설정 한 줄 차이다.

JWKS 캐시는 호출 자체를 없애므로 위 위험도 함께 줄인다. **동시성 모델을 바꾸기 전에 호출을 없애는
쪽이 싸다** 는 원칙이 여기서도 적용된다.

## Consequences

**얻는 것**

- 구속 자원의 정체와 `천장 = 자원 ÷ 점유 시간` 관계를 세 지점에서 4% 오차 안으로 확정.
- 기술 선택의 **적용 범위**를 측정으로 확정 — 가상 스레드는 인증 경로에만 유효.
- "서버를 키우면 된다"가 통하지 않는 영역을 수치로 구분 (포화 시 CPU 3.1%).
- 재현 가능한 하네스 + Grafana 관측 스택 (`watch.sh` 한 줄로 누구나 재현).

**운영 영향: 현재 0.** D4 로 미적용. 실험 코드는 `@Profile("loadtest & !prod")` 격리.
`docs/research/` 는 git 추적 대상이므로 측정 원본이 리포에 남는다.

**Trade-off (D4 적용 시)**

- 런타임 JDK 21 로 올려야 한다 (`Dockerfile` 런타임 스테이지 Corretto 17 → 21).
- 가상 스레드는 **무제한 동시성**이다 — 외부 의존이 느려지면 백엔드가 버티는 대신
  외부 서비스에 부하를 그대로 전가한다. 그래서 후보 ③(bulkhead)이 **짝으로 필요**하다.
  D4 단독 적용은 문제를 하류로 미루는 것이다.

**지금 적용할 것**: D11 참조 (인증 경로 타임아웃 · JWKS 캐시 · graceful shutdown).
본 ADR 의 주 후보(가상 스레드)는 보류지만, 이 세 건은 별도 PR 로 즉시 처리한다.

**재발 방지 — 하네스 결함 3건** (`docs/agent/learning.md` 후보)

1. **실행 중 bash 스크립트 편집 금지.** bash 는 스크립트를 증분으로 읽어, 편집하면 바이트
   오프셋이 어긋나 엉뚱한 줄에서 재개된다. 측정 1회가 오염돼 폐기했다.
2. **Testcontainers 의 조용한 스킵.** colima 는 소켓이 `~/.colima/default/docker.sock` 라
   Testcontainers 가 "Docker 없음"으로 판정, `disabledWithoutDocker=true` 로 **31건이 스킵되는데
   빌드는 SUCCESSFUL** 이었다. → `build.gradle.kts` 의 test 태스크가 소켓을 탐지해 `DOCKER_HOST` 주입.
3. **`@Container` + Spring 컨텍스트 캐시 충돌.** `@Container` 는 클래스마다 start/stop 인데
   베이스 클래스의 static 컨테이너를 하위 4개 클래스가 공유해, 먼저 끝난 클래스가 컨테이너를
   내리면 캐시된 컨텍스트가 **죽은 포트**를 물었다(`Connection refused`).
   → 싱글턴 컨테이너 패턴. 결과: 274건 전부 통과, 스킵 31 → 1, 소요 2m23s → 45s.

**후속**

- 시나리오 2: 과부하 방어(load shedding / bulkhead) — D4 의 짝.
- W-MIX 측정: 외부 포화가 DB 작업을 굶기는 전이 현상 — ③의 필요 근거.
- 선행 개선 PR (타임아웃 · JWKS 캐시 · graceful shutdown).
