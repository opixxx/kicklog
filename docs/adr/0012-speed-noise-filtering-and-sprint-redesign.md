# ADR-0012: GPS 노이즈 정제 파이프라인 + 스프린트 지표 재설계 (14→20 km/h, 고강도 러닝 분리)

- **Status**: Accepted
- **Date**: 2026-07-11
- **선행 ADR**: ADR-0001 D8 (스프린트 정의 — 본 ADR 이 supersede), ADR-0004 D8 (집계 캐시 + algorithmVersion Hybrid 진화 예고)
- **설계 SoT**: 분석 아티팩트 "KickLog 최고속도, 뭐가 문제고 어떻게 고치나" (artifact `c41d9708`, 섹션 8 확정 설계)
- **실측 데이터**: 애플 건강 내보내기 (2026-05-29 추출, 축구 워크아웃 42개 / 2026-05-28 경기 3쿼터 상세)
- **구현**: `ios/KickLog/Services/SpeedMetricsCalculator.swift` (+ 실측 픽스처 테스트 `ios/KickLogTests/`)

## Context

경기 상세의 최고속도가 33 km/h — 우사인 볼트 최고 시속(37.6)에 육박하는 비현실 수치가 그대로 노출됐다.
실측 export 분석으로 확인한 데이터의 실체:

- 축구 워크아웃엔 **runningSpeed 샘플이 0개, GPS 루트도 0개** (4년치 전체). 속도의 유일한 재료는
  Watch 가 남기는 **2~3초짜리 `distanceWalkingRunning` 조각**의 거리/시간 derive 뿐.
- GPS 점프 한 방이면 조각 하나가 40~51 km/h 가 된다. 기존 필터(35 km/h 초과 컷)는 초대형 점프만
  걸러서 **30~34 km/h 대 노이즈가 "합법적으로" 최고속도가 됐다** (1쿼터 실측: 원본 max 51.4 → 컷 후 33.0).
- 기존 스프린트(14 km/h·3초 지속)는 **경기당 83회** 잡힘 — 14 km/h 는 스포츠 과학에서 러닝 존 시작이라
  적당히 뛴 것까지 전부 집계. 게다가 샘플 하나가 이미 2~3초라 **3초 지속 조건이 GPS jump 한 방으로 뚫림**.
- iPhone 을 소지하고 뛰면 **iPhone 과 Watch 가 같은 시간대 거리를 각자 기록** (실측: 워크아웃 30개에서
  시간 겹침, 최대 2,406초 / iPhone 기여 0.1~1.8 km) → 전체 합산 시 거리 이중 집계.
- 샘플 밀도는 **이봉분포**: 라이브 기록 = 샘플 duration 중앙값 2~3초 vs 뭉텅이 기록 = 383~726초.
  뭉텅이는 2021~2023 에 몰려 있지만 **2024-05-01 경기도 뭉텅이** — "2023년 이전" 같은 날짜 기준은 틀린다.

## Decisions

### D1. 정제 파이프라인 — 통계 필터 대신 물리 규칙 (모든 속도 지표 공유)

1. **Watch 소스 필터**: Watch 샘플이 있으면 Watch 만 사용 (거리 합산 포함 — 이중 집계 제거).
   Watch 부재 시 전체 사용 (단일 소스면 이중 집계가 없음).
2. **35 km/h 초과 컷**: 시계열에서 완전 제거 (이웃 판정에도 미사용 — 노이즈이므로).
3. **고립 스파이크 기각**: ≥18 km/h 샘플의 양옆 이웃(각 3초 이내 존재)이 **둘 다 걷기 속도(<7 km/h)**
   면 기각. 사람은 한 샘플(2~3초) 만에 걷기→전력질주→걷기가 물리적으로 불가능하고, 진짜 질주는
   반드시 가감속 램프(이웃 흔적)를 남긴다.
4. **한쪽 공백 + 반대쪽 ≥7 km/h** → 램프의 일부로 보고 유지.
5. **판별 불가(한쪽 이상 공백 + hot 이웃 없음)** → D3 심박 교차검증이 최종 심급.

**기각한 대안 — Hampel/MAD 통계 필터**: 시뮬레이션 결과 걷기 중 진짜 전력질주(12→21→25→24 램프)의
최고 샘플들을 노이즈로 오판해 잘라냈다. 실제 판정을 좌우한 건 통계 밴드가 아니라 "양옆에 가감속
흔적이 있는가" 라는 물리 규칙 — 그래서 규칙만 남기고 통계 기계는 걷어냈다. 정지 출발 스프린트는
앞쪽이 "샘플 공백"으로 나타나므로 3번 규칙에 구조적으로 걸리지 않는다 (요구: 진짜 질주 보존).

### D2. 지표 재정의 — 스프린트 20/17, 고강도 러닝 14/12 (히스테리시스)

- **스프린트 = 진입 20 / 이탈 17 km/h, 단일 샘플 인정**. FIFA 트래킹 표준(순간속도 25.2 km/h, 1초
  이상)의 **2~3초 평균 보정판** — 순간 25 km/h 질주가 2~3초 평균으론 20~22 로 깎여 기록되고, 샘플
  하나가 이미 2~3초라 "1초 이상"은 자동 충족. 진입/이탈 분리로 임계선 출렁임(18점대 한 샘플)에
  1회가 2회로 쪼개지는 것을 방지. **샘플 공백 3초 초과 시 질주 분리** (공백을 못 보고 두 질주를
  이어붙이거나, 노이즈 한 방이 지속 조건을 채우는 것 방지). 단일 샘플 에피소드는 D1-3 판정 재적용.
- **고강도 러닝 = 진입 14 / 이탈 12 km/h** — 기존 스프린트 지표의 rename. 지표를 버리지 않고
  "적당히 뛴 활동량"으로 나란히 표시.
- **최고속도 = 정제 후 max.**
- 실측 검증(2026-05-28): 스프린트 쿼터별 **7 / 13 / 16**, 최고속도 **28.5 / 34.1 / 29.4**,
  고강도 러닝 **25 / 25 / 28**. (Q2 34.1 은 심박 +15 bpm 급등으로 생존한 진짜 이벤트 — 숫자는 GPS 가
  부풀렸을 수 있지만 이벤트는 실재.) 임계 20 vs 21 최종 dial 은 다음 경기 체감 횟수와 비교해 확정.

### D3. 심박 교차검증 — "직전 40초 평균 +5 bpm OR 세션 최고심박의 95%"

속도만으로 판별 불가한 이벤트는 **직후 45초 내 최대 심박**이 (a) 직전 40초 평균 대비 **+5 bpm 이상**
급등하거나 (b) **세션 최고심박의 95% 이상이면서 직전 평균보다 상승**했으면 진짜로 인정. (b) 의
상승 조건은 테스트가 잡아낸 허점 보완 — 심박이 완전히 평탄한 세션은 세션 최고 == 현재 수준이라
95% 규칙이 항상 통과해버린다 (조깅 중 GPS 스파이크 오인). (b) 는 후반 고심박 상태 보호 —
실측에서 3쿼터 27.8/26.2 km/h 질주는 이미 심박 181~184(최고 193 의 94~96%)라 급등 폭이 +2~3 에
그쳤다. GPS 는 속일 수 있어도 심장은 못 속인다는 독립 증거 활용. **심박 데이터 부족 시 보수적으로
기각** — 노이즈를 최고속도로 올리는 것보다 이벤트 하나 놓치는 게 낫다.

### D4. 저밀도 데이터 = "계산 불가" (0 이 아니라 숨김)

**샘플 duration 중앙값 ≤ 10초 AND 커버리지(샘플 duration 합/분석 구간) ≥ 30%** 일 때만 최고속도·
스프린트·고강도 러닝을 계산. 미달이면 `speedMetricsAvailable=false` → UI 는 "—" 표시.
날짜 기준이 아니라 데이터 기준 (2024년에도 뭉텅이 경기 실재). 거리·평균속도·심박·kcal 은 뭉텅이
데이터에서도 유효하므로 계속 표시. Match 헤드라인은 신뢰 가능한 쿼터만 집계하고, 전 쿼터가
계산 불가면 헤드라인도 계산 불가.

### D5. algorithmVersion 재분석 — ADR-0004 D8 (C) Hybrid 진화 실행

`QuarterWorkout.analysisVersion` (기존 행 기본값 1, 현행 2) 도입. 앱 구동 시 뒤처진 쿼터를
HealthKit raw 로 일괄 재분석 (`WorkoutAnalyzer.reanalyzeOutdatedQuarters`). trim 된 쿼터는 저장된
구간으로 분석해 trim 보존. HK 원본을 못 찾은 경우: UUID 형식이 아닌 쿼터(서버 복구분 `server-...`)만
버전을 올려 재시도를 중단하고, 실제 UUID 는 권한 미허용/HK 동기화 지연일 수 있어(read 권한 상태는
프라이버시상 조회 불가) 다음 구동에 재시도한다 — 일시적 부재를 영구 스킵으로 오판하지 않기 위함
(코드 리뷰 M1). 스윕은 재진입 가드로 중복 실행을 막는다 (리뷰 M2).

### D6. 백엔드 무변경 (후속 PR 로 분리)

시즌 집계는 저장값 `maxOfOrNull` 이라 SQL 수정 불필요. 계산 불가 쿼터는 PUT 에 0 전송 — 시즌 best
에서 0 은 절대 안 이기므로 무해. **알려진 비대칭 (리뷰 M3)**: 서버 응답엔 계산 불가 플래그가 없어
같은 경기가 본인 화면에선 "—", 친구 화면에선 "0회" 로 보인다. **알려진 한계 (리뷰 m5)**: Watch
소스 필터는 "존재 시 전량 대체"라 Watch 가 경기 중 방전되고 iPhone 이 후반을 기록한 케이스는 후반
거리가 누락된다 (저밀도 커버리지 체크가 계산 불가로 잡아줄 여지는 있음).
**후속**: 고강도 러닝 동기화 + 계산 불가 nullable 전파(DTO/엔티티/Flyway) +
`SeasonStatService.best()` 0 제외 필터 + `FriendMatchDetailScreen` 고강도 러닝 표시.

## Consequences

- 33 km/h 같은 노이즈 최고속도 소멸 (실측: 정제 후 최고 34.1 — 심박이 증언하는 진짜 이벤트만 생존).
- 스프린트가 "폭발 질주" 만 세는 지표가 됨 (83→36회/경기). 기존 수치와 불연속 — 재분석으로 과거
  경기도 일괄 재계산되므로 앱 내 일관성은 유지되나, 서버의 옛 집계값은 재동기화 전까지 다를 수 있음.
- 2021~2024 뭉텅이 경기들은 최고속도·스프린트가 "—" 로 바뀜 (정직성 > 엉터리 수치).
- 임계·심박 기준은 코드 상수로 명시 (`SpeedMetricsCalculator`) — 다음 경기 실측과 체감 비교로 dial 예정.
