# ADR-0001: MVP 스코프 결정

- **Status**: Accepted
- **Date**: 2026-05-21
- **방법**: `/grill-me` 인터뷰 (12개 결정 + 친구 기능 추가)

## Context

조기축구 경기 데이터를 애플워치 + HealthKit으로 측정해 개인 리포트를 제공하는 iOS 앱(`KickLog`)의 MVP 스코프를 정의해야 함. 본 ADR은 각 결정의 옵션 비교와 채택 이유를 영구 기록한다.

---

## Decisions

### D1. 배포 방식 / 사용자 범위

- **선택**: 본인 + 축구팀 (iOS 사용자) 시작, 최종 목표 앱스토어 정식 출시
- **고려한 옵션**:
  - 사이드 프로젝트 한정 (배포 X)
  - TestFlight 베타까지만
  - 정식 출시 (선택됨)
- **이유**: 사용자 본인의 학습/포트폴리오 가치 + 가족·지인 접근성. 단 1차는 TestFlight로 본인+팀원에게 배포해 한 시즌 사용 후 정식 출시.

### D2. 데이터 공유 모델

- **선택**: 1:1 양방향 친구 (MVP) / 팀 단위 (v1.1+)
- **고려한 옵션**:
  - (A) 본인 데이터 only — 백엔드 X
  - (B) 1:1 친구 (선택)
  - (C) 팀 단위
  - (D) 1:1 + 팀
- **이유**: 팀원 중 Android 사용자가 있어 팀 단위는 일부 멤버를 배제. 1:1 친구가 iOS 사용자끼리 자연스럽게 연결되고, 향후 1:1 그래프 위에 팀 개념을 추가하기 쉬움 (역방향은 어려움).

### D3. 플랫폼 — watchOS 자체 앱?

- **선택**: 자체 watchOS 앱 없음. Apple 기본 운동 앱의 Soccer 워크아웃 사용
- **고려한 옵션**:
  - Apple 기본 운동 앱 사용 (선택)
  - 자체 watchOS 앱 (실시간 표시, 자동 쿼터 분할)
- **이유**: MVP 비용 최소화. 워치 앱이 추가하는 가치(자동 쿼터 분할, 실시간 표시)는 사용자가 쿼터마다 워크아웃을 직접 시작/종료하기로 한 결정과 잘 맞아떨어져 우선순위 낮음. v2 후보.

### D4. 경기 구조

- **선택**: 25분 × 4쿼터 (조기축구 한정)
- **고려한 옵션**: 전후반(축구) / 4쿼터(조기축구) / 풋살(2~3 피리어드)
- **이유**: 사용자의 실제 조기축구 환경은 2시간 = 25분 × 4쿼터. 사용자가 출전한 쿼터마다 워치에서 워크아웃 토글 → HealthKit에 25분짜리 워크아웃 1~4개로 깔끔하게 분리됨 → 분석 segment 로직 불필요.

### D5. MVP의 종목 — 풋살 포함?

- **선택**: 조기축구 only (풋살은 v2)
- **고려한 옵션**:
  - (A) 조기축구 only (선택)
  - (B) 둘 다, 통합 처리
  - (C) 둘 다, 풋살은 일부 지표만
- **이유**: 풋살은 실내 = GPS 없음 → 거리·최고속도·스프린트 측정 불가 또는 가속도계 추정치(부정확). 둘 다 지원하면 데이터 모델 분기 + 핵심 차별화(GPS 기반 지표) 약화. 조기축구만으로 코어 검증 후 v2에서 풋살 추가.

### D6. 경기 식별 / 라벨링 흐름

- **선택**: 자동 그룹핑 + 사용자 확정 체크박스
- **고려한 옵션**:
  - (A) 완전 자동 추론
  - (B) 자동 그룹핑 + 사용자 확정 (선택)
  - (C) 사용자가 매 쿼터마다 폰에서 라벨링
- **이유**: (A)는 사용자가 일부 쿼터만 출전한 경우(워크아웃 3개 = 1·3·4쿼터?) 자동 추론 불가능 → 데이터 신뢰 깨지면 끝. (C)는 운동장에서 매 쿼터마다 폰 켜야 함 → 비현실적. (B)는 경기 후 카페에서 체크박스 클릭 한 번이면 끝, 데이터 정확도 보장.

### D7. 종료 깜빡함 처리

- **선택**: 30분 초과 워크아웃 감지 → 경고 + 시작/종료 시각 슬라이더로 사용자 수동 trim
- **고려한 옵션**:
  - (A) 무시 — 그대로 사용
  - (B) 자동 감지 + 자동 trim
  - (C) 경고 + 수동 trim (선택)
  - (D) MVP는 (A), v1.1에서 (C) 추가
- **이유**: 정식 출시 목표라 데이터 신뢰 깨지면 앱스토어 1점 직행. (B) 자동 trim은 골 세레모니·부상 체크 등 정당한 정지 구간을 잘못 잘라낼 위험. (C)는 80% 정상 케이스엔 슬라이더 안 뜸, 깜빡한 20%만 사용자가 직접 자르면 됨 → 마찰 최소 + 신뢰 보장.

### D8. 스프린트 횟수 정의

- **선택**: 절대 임계 **14 km/h 이상 3초 이상 지속** (코드 상수, 화면에 기준 표기)
- **고려한 옵션**:
  - (A) FIFA 표준 19.8 km/h
  - (B) 아마추어 절대 임계 14 km/h (선택)
  - (C) 개인화 (본인 최고속도의 80%)
  - (D) 심박수 기반
  - (E) MVP에서 빼기
- **이유**: (A)는 아마추어가 거의 못 넘김 → 평생 0회 위험. (C)는 콜드 스타트(첫 경기 데이터 없음) + GPS 노이즈 한 번이면 임계 24km/h 됨 → 풋살 같이 측정 불안정. (D)는 "심박 올랐다고 스프린트?" 직관 어긋남. (B)는 단순·결과값 적당(경기당 10~30회). 본인+팀원 한 시즌 후 (C) 개인화로 진화 검토.

**속도 산출 알고리즘 (2026-05-29 보강):**
- 1순위: `runningSpeed` (HKQuantityType) 샘플 사용
- 2순위 (fallback): `distanceWalkingRunning` 샘플 (Apple Watch 가 2~3초 단위로 기록) 의 `(거리 / 실제 duration)` 으로 구간 속도 derive
- 자동감지 워크아웃은 `runningSpeed` 가 거의 비어있어 fallback 이 사실상 주 경로
- **Sanity cap: 35 km/h 초과는 GPS jump 노이즈로 간주해 제외** (인간 한계 ~37 km/h, Bradley et al. 엘리트 sprint 25.2 km/h). 야간 운동장의 GPS 멀티패스 + 가속도계 fusion 오차로 40~50 km/h 같은 비현실 샘플이 가끔 발생.
- 평균: 구간 duration 가중평균 / 최고: 구간 중 max / 스프린트: 14 km/h 이상 연속 구간의 누적 duration ≥ 3초 마다 +1

### D9. 쿼터별 체력 변화 척도

- **선택 (2026-05-29 개정)**: **이동거리 + 평균 심박 + 스프린트 횟수** — 3종 막대그래프 동시 표시. + 출전 쿼터별 상세 카드 (운동시간/이동거리/최고속도/평균심박/최고심박/kcal).
- **고려한 옵션**:
  - 단일 척도 (평균 심박 / 평균 속도 / 스프린트 횟수 / 심박 회복)
  - **세 척도 동시 표시 (선택)**
  - 단일 "체력 점수 0~100"
- **이유**: 단일 척도는 노이즈(워밍업 부족, 전술 변수)로 오해 가능. 세 척도가 모두 같은 방향으로 떨어지면 그것이 진짜 체력 저하 — 사용자가 본인 패턴을 직접 발견하게 함. "체력 점수"는 매력적이지만 "왜 78점?" 설명 불가 → 한 시즌 후 신뢰 잃음.
- **평균속도 → 이동거리 변경 사유**: 평균속도 7~8 km/h 는 걷기/달리기/정지가 혼합된 값이라 사용자가 "이 쿼터에 얼마나 활발했나" 직관적으로 해석 어려움. 이동거리는 "이 쿼터에 얼마나 뛰었나" 가 한눈에 보임.
- **쿼터별 상세 카드**: 막대그래프(trend) 아래에 출전 쿼터마다 6 metric 카드. trend 확인 후 그 쿼터의 detail (예: "Q2 가 활동량 ↑ 인데 최고심박 195 까지 갔구나") 까지 한 화면에서 비교.

### D10. 메타데이터 입력 범위

- **선택**: 상대팀 + 결과(승무패) + 포지션(GK/DF/MF/FW) + 본인 골 + 본인 어시 + 운동장 — **모두 optional**. 평점·코멘트 제외.
- **고려한 옵션**: 최소/기본/중간/풍부/매우 풍부
- **이유**: "축구 **기록** 앱"이려면 경기 맥락(누구랑·결과·골)이 필요. 자동 측정 불가능한 정보(골/어시)는 안 받으면 영영 없음 → 시즌 누적 통계가 단순 운동 기록으로 전락. 입력 마찰은 모두 optional + 라벨링 화면에서 한꺼번에 + 골/어시는 ± 스테퍼로 해결. 평점/코멘트는 사용자 입력 마찰 대비 가치 낮아 v1.1+.

### D11. 운동장 인식

- **선택**: GPS 좌표 자동 매칭. 첫 등록만 사용자가 이름 지정.
- **이유**: 본인이 자주 가는 운동장이 2~5개로 한정 → 한 번 등록하면 다음부터 GPS 좌표(반경 100m)로 자동 인식. 입력 마찰 거의 0.

### D12. 탭 구조 / 리포트 / 시즌

- **선택**: **4탭 (경기 / 시즌 / 친구 / 설정)**, 한 경기 리포트는 **단일 페이지 스크롤**, 시즌은 **자동 연도별** (캘린더 연도 기준)
- **이유**: 단일 페이지 스크롤은 시선 흐름 자연스럽고 캡처 한 번에 가능(단톡방 공유 ←핵심 retention 채널). 시즌은 사용자 정의 기간보다 캘린더 연도가 직관적 + 자동.

### D13. 진입 흐름 (MVP)

- **선택**: Passive(사용자가 앱 직접 열기) + HealthKit Observer Query(백그라운드 자동 import). 푸시 알림은 v1.1.
- **이유**: 본인+팀원 = 매주 1~2회 경기 = 앱 여는 빈도 충분. 푸시 인프라(Observer Query + Background Task + APNs)는 MVP 일정 2~3주 추가 비용. v1.1에서 별도.

### D14. 친구 추가 / 공개 범위

- **선택**:
  - 추가: **초대 링크(메인) + 사용자명 검색(보조)**
  - 관계: 양방향 승인
  - 공개: 전부 공개 + "심박수를 친구에게 숨기기" 토글 1개
  - 업로드: 라벨링 완료 시 자동
- **이유**: 조기축구는 단톡방 존재 → 초대 링크가 가장 자연스러움. 양방향 승인은 HealthKit 데이터(민감) 특성상 필수. 경기별/지표별 세밀 권한은 마찰만 큼 → 단일 토글로 단순화. 친구 기능 사용자는 이미 공유 의도가 있으므로 자동 업로드.

### D15. 백엔드 도입 여부

- **선택**: 처음부터 Spring Boot 백엔드 동시 개발 (D2의 친구 기능이 백엔드를 필수로 만듦)
- **고려한 옵션**:
  - (I) iOS only — 백엔드 X
  - (II) 백엔드 동시 (선택)
  - (III) iOS 먼저 → 백엔드 나중
- **이유**: 친구 기능은 백엔드 없이 불가능. 사용자가 백엔드 본업(Java/Kotlin + Spring)이라 백엔드 구축이 부담이 아닌 강점. 단계적(III)은 본인 데이터만 → 친구 기능 전환 시 데이터 모델·인증 흐름·UI 대수술 필요 → 처음부터 친구 가정 설계가 더 깔끔.

### D16. 기술 스택 / 인프라

- iOS: Swift / SwiftUI / SwiftData / Swift Charts / **iOS 26.4+** / SPM / Swift Testing / MV 아키텍처
- Backend: Kotlin / Spring Boot 3 / Java 17 / PostgreSQL 15 / Gradle / Flyway / Spring Security (JWT) / REST
- 호스팅 예정: Railway 또는 Fly.io
- Repo: GitHub Private (`opixxx/kicklog`), 모노레포 (ios/ + backend/ + docs/ + infra/)
- Bundle ID: `com.opixxx.kicklog`

## Consequences

### 긍정
- 풀스택 포트폴리오 (iOS + Spring 백엔드) 결과물
- 데이터 정확도 보장 흐름 (라벨링 + 30분 임계 + 슬라이더 trim)
- 친구 기능으로 retention 채널 확보 (단톡방 캡처 → 앱 안 공유로 흡수)
- 백엔드의 정당성이 명확 ("친구 데이터 read API" 라는 필연적 책임)

### 부정 / 트레이드오프
- MVP 일정 10~14주 (iOS only 대비 2~3배)
- 운영비 발생 (월 $5~15 백엔드 호스팅)
- 1인 개발 burnout 위험 → 마일스톤 분리·주간 진척 체크 필수
- Apple HealthKit 데이터 서버 전송 정책 준수 필요 (사용자 동의 + 명분 명시)

### 후속 결정 (이후 ADR)
- **ADR-0002: 자동 그룹핑 시간/위치 임계값 ✅ 작성 완료 (2026-05-21)** — 시간 90분 + 위치 100m (Haversine)
- **ADR-0003: 백엔드 데이터 모델 / API 스키마 ✅ 작성 완료 (2026-05-21)**
- **ADR-0004: SwiftData 모델 + HealthKit 매핑 ✅ 작성 완료 (2026-05-21)** — 본인/친구 모델 분리, 최소 권한 6개, Observer Query + Background Delivery, UTC + Local TZ, 친구 캐시 1h TTL, 사용자 프로필 안 받음, SwiftData 영속 캐시
- ADR-0005: 초대 링크 Universal Link 구조 (pending)
- **ADR-0006: 백엔드 호스팅 선택 ✅ 작성 완료 (2026-05-21)** — AWS EC2 + RDS + Terraform (서울 region)
