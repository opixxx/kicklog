# ADR-0014: 시즌 통계 집계를 애플리케이션에서 DB 로 — EXPLAIN 만으로는 판단할 수 없었다

- **Status**: Accepted
- **Date**: 2026-09-16
- **선행 ADR**: ADR-0003 D9.1 (시즌 집계는 백엔드 derive), ADR-0009 (free-tier 운영), ADR-0011 (복제 부하테스트 iteration 1)
- **관련 PR**: #84/#85 (컨테이너 메모리 제한 + JVM heap 상한 — 2026-09-06 장애 대응)
- **측정 산출물**: 본 ADR "측정" 절 (EXPLAIN · 할당량 A/B)

## Context

### 결정과 구현이 어긋나 있었다

ADR-0003 D9.1 은 "본인/친구 시즌·월별 집계 = **백엔드 SQL derive**" 로 결정했다.
그런데 실제 `SeasonStatService.calculate()` 는 **SQL 이 아니라 애플리케이션에서** 집계하고 있었다.

```kotlin
val matches = findAllByUserIdAndPlayedAtBetween(userId, start, end)   // 1년치 전부 JVM 으로
totalDistanceM = matches.sumOf(Match::totalDistanceM)                 // Kotlin 에서 합산
quarterCount   = matches.sumOf { it.quarters.size }
```

쿼리는 `SELECT DISTINCT m ... LEFT JOIN FETCH m.quarterWorkouts` 로 **행을 가져오기만** 했고
`SUM`·`COUNT`·`GROUP BY` 가 없었다. D9.1 의 "derive" 를 "저장하지 않고 조회 시점에 계산" 으로
읽으면 충족이지만, "SQL derive" 라는 문언이 가리키는 곳과 구현은 달랐다.
경기 N 건이면 엔티티 **N + 4N 개**가 힙에 생성된다.

### 조건이 바뀌었다

원래도 비효율이었으나 2026-09-06 장애가 전제를 바꿨다. 컨테이너 메모리 제한이 없어 JVM 이
heap 상한을 **642MB** 로 잡았고, 그것이 호스트 page cache 를 고갈시켜 9일간 마비시켰다
(PR #84/#85). 대응으로 `mem_limit: 512m` + `-Xmx224m` 을 적용해 **heap 여유가 3분의 1** 이 됐다.

그 결과 "1년치를 통째로 메모리에 올리는" 방식이 감수하던 비용이 리스크가 됐다.
친구 통계까지 조회하면 같은 부하가 배수로 붙는다.

## 측정

전환 여부를 추측으로 정하지 않았다. 두 축을 따로 쟀다.

### ① DB 실행 계획 — `EXPLAIN (ANALYZE, BUFFERS)`

PostgreSQL 16 · `matches` 30만 행 / `quarter_workouts` 120만 행 (ADR-0011 과 같은 규모) ·
사용자당 경기 300건.

| | 기존 (행 조회 1회) | 신규 (집계 3회) |
|---|---|---|
| 실행 시간 | 12.696 ms | **12.093 ms** |
| Buffers | 2,425 | **3,024** |
| 반환 행 | **1,200** | **14** |
| 부가 작업 | Sort(quicksort 199kB) + Unique | 없음 |

세 쿼리 모두 `idx_matches_user_played_at_id` 를 정상적으로 탄다 (마이그레이션 불필요).

**DB 시간은 사실상 같고 버퍼는 오히려 늘었다** — `matches` 를 3번 스캔하기 때문이다.
즉 **"DB 가 더 잘하니까" 는 이 규모에서 근거가 되지 못한다.**

### ② 애플리케이션 힙 할당 — A/B

같은 측정 하네스를 두 브랜치에 넣고 **각각 별도 JVM** 으로 실행했다 (GC 귀속을 섞지 않기 위해).
JFR 샘플링 대신 `ThreadMXBean.getThreadAllocatedBytes` 로 스레드 누적 할당 바이트를 직접 읽었다.
Testcontainers PostgreSQL 16 · 사용자 1명 · 경기 300건 × 쿼터 4개 · warm-up 200회 후 1,000회.

| 지표 | 애플리케이션 집계 | DB 집계 | 배수 |
|---|---|---|---|
| **호출당 힙 할당** | 2,726.2 KB | **116.6 KB** | **23.4× ↓** |
| 총 할당 (1,000회) | 2,662.3 MB | 113.8 MB | 23.4× ↓ |
| **GC 횟수** | 47 | **1** | **47× ↓** |
| GC 누적 시간 | 43 ms | 1 ms | 43× ↓ |
| 호출당 시간 | 8.186 ms | 4.115 ms | 1.99× ↓ |

> 두 측정의 시간 수치를 직접 비교하지 말 것 — ①은 30만 행 테이블, ②는 300행이다.
> DB 측 절대 시간은 비교 불가이나, **애플리케이션 할당은 사용자당 경기 수에만 의존**하므로 유효하다.

## Decisions

### D1. 시즌 통계 집계를 **DB 로 내린다**

- **판단 근거는 DB 지표가 아니라 할당 지표다.** ①만 봤다면 "바꿀 이유 없음"(시간 동일·버퍼 증가)이
  결론이었다. 실제 차이는 반환 행 1,200 → 14, 엔티티 약 1,500개 → 0 이고 `EXPLAIN` 으로는 보이지 않는다.
- heap 224MB 제약에서 GC 47회 → 1회는 유의미하다. 데이터가 쌓일수록 기존 방식은 선형으로 늘고
  집계 방식은 거의 일정하다.
- ADR-0003 D9.1 의 "SQL derive" 문언과 구현을 일치시킨다.

### D2. 쿼리를 **집계 단위별로 분리**한다 (경기 / 쿼터 / 월별)

- `matches` 와 `quarter_workouts` 를 조인해 한 번에 집계하면 경기 1행이 쿼터 수만큼 복제되어
  거리·골이 **쿼터 개수배로 중복 합산**된다 (fan-out). 왕복 1회로 줄이는 것보다 값 정확성이 우선이다.
- DTO 도 `SeasonMatchAggregate` / `SeasonQuarterAggregate` 로 나눠 "단위를 섞지 않는다" 를
  주석이 아니라 **타입으로** 표현한다.
- 쿼리 ②의 조인은 기간 필터 용도이고 집계 대상이 쿼터 하나뿐이라 fan-out 이 없다.

### D3. **나눗셈은 SQL 이 아니라 애플리케이션**에서 한다

- 평균 심박은 `SUM(hr × dur)` 과 `SUM(dur)` 을 분자·분모 그대로 받아 Kotlin 에서 나눈다.
- SQL 에서 나누면 0 division 과 정수 버림을 SQL 문법으로 처리해야 하고, 기존 구현과
  **반올림이 어긋날 위험**이 있다. api-spec §8.1 이 "정수, 소수점 버림" 을 계약으로 못 박았다.

### D4. 세 쿼리를 **REPEATABLE_READ 로 한 스냅샷에 묶는다**

- 전환 전에는 쿼리가 1개라 원자적이었다. 3개로 나누면 PostgreSQL 기본 격리(READ COMMITTED)에서
  **statement 마다 스냅샷이 갱신**되어, 조회 도중 경기가 커밋되면 `matchCount=2` 인데
  `quarterCount` 는 3번째 경기까지 포함하는 자기모순 응답이 나갈 수 있다.
- readOnly 트랜잭션이라 추가 잠금이 없어 비용은 사실상 0. **동작 보존을 위한 필수 조치**다.
- 이 축은 테스트로 구조적으로 잡히지 않는다 (코드 리뷰에서 발견).

### D5. **UTC 월 기준을 SQL 에 명시**한다

- `EXTRACT(MONTH FROM played_at AT TIME ZONE 'UTC')`. 빠뜨리면 서버 타임존에 따라 경기가
  다른 달로 집계된다. api-spec §8.1 이 "UTC `playedAt.month` 기준" 으로 계약화했고
  기존 구현도 `atZone(ZoneOffset.UTC)` 였다.

## Consequences

**긍정**
- 호출당 할당 23.4배, GC 47배 감소. heap 224MB 제약에서 여유 확보.
- 데이터 증가에 대한 민감도가 선형 → 거의 일정으로 바뀐다.
- ADR-0003 D9.1 의 문언과 구현이 일치한다.

**부정 / 감수**
- **왕복이 1회 → 3회**로 늘었다. 같은 VPC 내 RDS 기준 약 1~2ms 추가이며, 측정에서 총 시간은
  오히려 줄었으므로 수용한다. 필요하면 `CROSS JOIN` 으로 2회까지 합칠 수 있다 (각 서브쿼리가 1행이라 안전).
- **버퍼 읽기가 늘었다** (2,425 → 3,024). `matches` 3회 스캔의 비용이다.
- `MatchStore` 인터페이스가 CRUD + 집계로 넓어졌다 (ISP). 현 규모에선 수용하고,
  커지면 `SeasonAggregateStore` 분리를 검토한다.
- native query 이므로 DB 방언에 묶인다. H2(테스트 프로파일)에서 `FILTER`·`AT TIME ZONE`·
  `CAST(... AS bigint)` 가 동작함을 사전 확인했다.

**측정하지 않은 것**
- 동시 부하 하에서의 거동. ADR-0011 iteration 2 (HikariCP 풀 상향 + non-burstable 인스턴스로
  천장 제거 후 사용자당 경기 수 50/200/500 기울기 비교)가 후속이다.

## 교훈

**DB 최적화의 근거를 DB 지표에서만 찾으면 틀린다.**

"집계는 DB 가 잘한다" 는 일반론은 맞지만, 이 케이스에서 `EXPLAIN` 은 **바꾸지 말라고 말하고 있었다**
(시간 동일, 버퍼 증가). 실제 이득은 DB 밖 — 엔티티 매핑과 힙 할당 — 에 있었고 그건 실행 계획에
나타나지 않는다. **측정 축을 하나만 잡으면 정반대 결론이 나올 수 있다.**

ADR-0011 에서 "복제 환경이면 코드 병목이 보일 것" 이라는 직관이 3층 구조에 막혔던 것과 같은 종류다.
가설을 세우고, **결론을 정하기 전에 재고**, 빗나가면 빗나간 대로 기록한다.

또 하나 — **리팩토링은 동작 보존이 전제인데, 원자성처럼 테스트로 잡히지 않는 축이 있다**(D4).
"기존 테스트가 전부 통과한다" 는 보존의 충분조건이 아니다.
